# ADR-004: Free-form string tags for themes and skills (no enforced enum)

## Status

Accepted

## Date

2026-06-10

## Context

Content is tagged by theme (and skills) so subsets can be selected for a given
leadership role (ADR-001). The tag vocabulary could be a closed enum validated at
build time, or free-form strings. The owner will author tags by hand across the
`work` collection and the `cv.ts` spine, and the set of useful themes will evolve
as projects are added.

## Decision

Use free-form string arrays for `themes` and `skills` (`z.array(z.string())` in
the `work` schema; `string[]` in `cv.ts`). No enforced enum. A recommended
starter vocabulary is documented for consistency but not validated:
`ai-llm`, `platform-devex`, `org-scaling`, `cloud-realtime-data`,
`security-compliance`, `transformation`.

## Alternatives Considered

### Alternative 1: Closed enum (`z.enum([...])`)

- **Description**: Validate themes against a fixed list; build fails on an unknown
  tag.
- **Pros**: Typo protection; a guaranteed-consistent set the Phase 2 variants can
  rely on.
- **Cons**: Adding a theme means a code change in two schemas; friction while the
  vocabulary is still settling; the owner wanted flexibility.
- **Why rejected**: The owner chose flexibility while the set is still forming.

## Consequences

### Positive

- The owner adds or renames themes freely without touching schemas.
- No build friction as the vocabulary evolves.

### Negative

- No build-time protection against typos or drift (`ai-llm` vs `ai_llm`).

### Risks

- Tag drift weakens selection over time. Mitigation: a documented recommended
  vocabulary, and (if drift becomes a problem) a later move to an enum is a small,
  additive change.

## Implementation Notes

The recommended vocabulary lives as a comment near the tag fields in
`content.config.ts` and `cv.ts` so it is visible at the point of authoring.
