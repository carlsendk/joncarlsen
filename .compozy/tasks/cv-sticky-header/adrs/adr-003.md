# ADR-003: A single shared Header component with a pathname-derived contextual back-link

## Status

Accepted

## Date

2026-06-10

## Context

PRD ADR-001 calls for one persistent header on every route carrying a contextual
back-link: `/cv → Overview (/)`, and `/impact`, `/work`, `/work/<slug>` → `Back
to CV (/cv)`, with no back-link on home. All five routes already share a single
`Base.astro` layout (props `title`, `description`, `ogImage?`) and today each
secondary page renders its own inline back-link `<nav>`.

The technical question was where the back-link's label and target come from. Two
honest options: the header derives them from the current path, or each page
declares them via a new layout prop. The site is static — the path is known at
build time for every generated page — so derivation is deterministic with no
runtime cost.

## Decision

Add one component, `src/components/Header.astro`, rendered once inside
`Base.astro` (replacing the current standalone `<ThemeToggle />` placement) as the
first element of `<body>`, so every route inherits it. The header **derives its
back-link from `Astro.url.pathname`** via a small internal pure function:

- `/` → no back-link.
- `/cv` → `{ href: "/", label: "Overview" }`.
- any other path (`/impact`, `/work`, `/work/<slug>`) → `{ href: "/cv", label:
  "Back to CV" }`.

Pages pass **no new props**; adopting the header means deleting each page's inline
back-link `<nav>`. The header's identity (name + title) is read from `cvData` and
rendered as a home link (`<a href="/">`), **not** as an `<h1>` — `Hero` keeps the
single page `<h1>`. Profile links are `cvData.links` filtered to LinkedIn and
GitHub.

## Alternatives Considered

### Alternative 1: Explicit `back` prop on Base.astro

- **Description**: `Base.astro` gains an optional `back={{href,label}}` prop each
  page sets; home omits it.
- **Pros**: No path-matching logic; fully explicit per page.
- **Cons**: Every page edits its `<Base>` call and must stay in sync; the
  back-link rule is already a deterministic function of the route, so the prop is
  redundant ceremony.
- **Why rejected**: More surface area and drift risk for zero benefit on a
  fixed, known route set.

### Alternative 2: Hybrid — derive with an optional override prop

- **Description**: Derive the default from pathname but allow a per-page override.
- **Pros**: Maximum flexibility.
- **Cons**: Adds an override path nothing currently needs.
- **Why rejected**: YAGNI; can be added later if a route ever needs a non-default
  back target.

## Consequences

### Positive

- One component owns the header; pages shed their inline nav blocks.
- Back-link cannot drift from the route — it is computed from it.
- Adding a future route under the CV hierarchy needs no header change (it falls
  through to the `Back to CV` default).

### Negative

- The derivation function encodes the route hierarchy in one place; a future
  route that should *not* map to `Back to CV` would need an explicit branch.
- The header reads `Astro.url`, coupling the component to being rendered within a
  page render (fine in Astro; it is always page-scoped here).

### Risks

- A new top-level route silently inherits `Back to CV`. Mitigation: the function
  is small and centrally located; new routes are reviewed against it.

## Implementation Notes

- The sticky header element needs a stable hook (e.g. `id="site-header"` or a
  class) so the print stylesheet can hide it — `Hero` also uses `<header>`, so a
  blanket `header { display:none }` in print is unsafe.
- Add `scroll-padding-top` on `html` (≈ header height) so in-page anchor targets
  are not hidden beneath the sticky bar; `scroll-behavior: smooth` already exists.
