# ADR-003: Class-based theming with per-theme accent tokens and an inline flash-guard

## Status

Accepted

## Date

2026-06-09

## Context

The PRD requires light AND dark themes: system-preference default, a manual toggle,
the choice remembered, AA contrast in both, no theme flash, and the near-zero-JS
posture preserved (client JS limited to the toggle). Tailwind v4 has no JS config
file in this project (it runs via PostCSS), so theming lives in CSS. A single
accent color cannot clear WCAG AA on both a white and a dark background.

## Decision

Drive dark mode with a **CSS class on `<html>`** using Tailwind v4's
`@custom-variant dark (&:where(.dark, .dark *))`. Define **semantic CSS custom
properties** (`--bg`, `--fg`, `--accent`, `--muted`, …) in `:root` for light and
override them under `.dark`; map them into utilities with `@theme inline`
(`--color-accent: var(--accent)`) so `text-accent`/`bg-accent` resolve to the
live, theme-switched value. The accent is a **per-theme pair**: cobalt
`#1d4ed8` (blue-700) on light, lightened `#60a5fa` (blue-400) on dark — both
verified AA. Dark base is a **soft near-black** (`~#0f1115`), not pure black.

Prevent the flash with **one `is:inline` blocking script in `<head>`** that, before
first paint, reads `localStorage.theme` (falling back to
`matchMedia('(prefers-color-scheme: dark)')`) and sets the `.dark` class. The
toggle button writes `localStorage.theme` and flips the class. This inline script
plus the toggle handler are the **only client JS** on the page.

## Alternatives Considered

### Alternative 1: `prefers-color-scheme` media query only (no toggle)

- **Pros**: zero JS, no flash.
- **Cons**: cannot honor a manual override or remember a choice.
- **Why rejected**: the PRD explicitly requires a manual, remembered toggle.

### Alternative 2: Single accent color for both themes

- **Pros**: one token to manage.
- **Cons**: blue-700 fails AA on dark; a mid-blue fails on white. No single value
  clears AA on both.
- **Why rejected**: violates the AA-in-both-themes requirement.

### Alternative 3: A UI framework / island for the toggle

- **Pros**: ergonomic state handling.
- **Cons**: ships a hydration runtime — breaks the near-zero-JS posture for a
  one-boolean control.
- **Why rejected**: a few lines of vanilla JS suffice.

## Consequences

### Positive

- Themes switch instantly with no flash; choice persists; JS stays minimal.
- Semantic tokens keep components theme-agnostic (`text-fg`, not `text-slate-900`).

### Negative

- Hand-maintained token tables for two themes; every new color goes through tokens.
- A small inline script in `<head>` (acceptable, documented).

### Risks

- Mis-tuned dark values could fail AA — verify both themes with a contrast pass.
- An inline script must stay tiny and dependency-free to avoid a CSP/perf cost.
