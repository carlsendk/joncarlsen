# ADR-003: Content layer - expanded typed data file plus an Astro content collection for case studies

## Status

Accepted

## Date

2026-06-09

## Context

`cv-content` introduces three tiers (frontpage, full CV, project deep-dives,
per ADR-001). The existing site stores all content in one typed file
(`src/data/cv.ts`, per `cv-site` ADR-003) holding a small `CvData` object. That file
must now carry far more structured CV data, and the project deep-dives are
long-form prose that does not belong in a TypeScript object.

Two forces: shared facts (name, roles, expertise, education) must stay
single-sourced so the frontpage and `/cv` never disagree and stay type-checked;
case studies are authored as prose and each needs its own URL.

## Decision

Split the content into two stores:

1. **Expanded typed data file (`src/data/cv.ts`).** Grow `CvData` to hold the full
   structured CV: profile/summary, areas of expertise, experience (each role
   with achievement bullets), education, certifications and networks,
   publications and honours, talks/writing links, a short about/narrative, and a
   compact personal-details block. The frontpage imports a subset; `/cv` imports
   the whole. This remains the single source of truth for structured facts and
   keeps TypeScript checking.

2. **Astro content collection `work` (`src/content/work/*.md`).** Each case
   study is one markdown file with typed frontmatter (title, slug, summary,
   role, period, metrics, order). A schema is defined with `defineCollection` +
   Zod in `src/content.config.ts`. A dynamic route `src/pages/work/[slug].astro`
   uses `getStaticPaths` over the collection to statically render one page per
   file. Frontpage and `/cv` query the collection to list/link case studies.

Adding a case study means dropping in a markdown file; no code or layout change.

## Alternatives Considered

### Alternative 1: Everything in markdown content collections

- **Description**: Move the CV body (roles, education, etc.) into collections too.
- **Pros**: Uniform authoring; all content as markdown.
- **Cons**: Loses TypeScript checking of structured facts; harder to share the
  same structured fields between frontpage and `/cv`; over-engineered for data
  that is fundamentally structured, not prose.
- **Why rejected**: Structured CV facts are better as typed data; only the
  long-form deep-dives benefit from markdown.

### Alternative 2: Single typed file for everything, no collection

- **Description**: Keep one `cv.ts`; store case studies as string fields.
- **Pros**: Simplest; no new concepts.
- **Cons**: Long prose in TS string literals is painful to author and read; no
  natural per-project URL; loses markdown formatting.
- **Why rejected**: Defeats the growable deep-dive capability the PRD requires.

## Consequences

### Positive

- Structured facts stay single-sourced and type-checked; prose lives in markdown.
- Case studies are first-class pages, added by dropping in a file.
- Cleanly extends `cv-site` ADR-003 rather than replacing it.

### Negative

- Introduces Astro content collections (a new concept in this repo) and a small
  schema to maintain.
- Two content stores instead of one; contributors must know which holds what.

### Risks

- Frontmatter drift from the schema. Mitigation: Zod schema fails the build on
  invalid frontmatter, catching errors early.
- `cv.ts` could grow large. Mitigation: it is plain data; split into typed
  sub-arrays within the one module if needed, still single-imported.

## Implementation Notes

- Astro's content collections are built in; `astro:content` provides
  `getCollection`. No new runtime dependency.
- Headshot uses `astro:assets` `<Image>` with the source in `src/assets/`
  (build-time optimization), rendered on the frontpage only; `/cv` stays clean
  for parsing and print.
- `/cv` ships with an `@media print` stylesheet (hide toggle/grain/nav, light
  ink-on-white, sensible page breaks) to provide a clean printable CV.
