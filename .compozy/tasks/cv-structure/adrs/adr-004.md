# ADR-004: Per-section lead-ins sourced from a central `sectionLeadIns` map in cv.ts

## Status

Accepted

## Date

2026-06-11

## Context

PRD Core Feature 2 adds a one-line lead-in under each section heading, and the
owner story requires content "maintained in one place." Every section is a
self-contained component that today reads its slice of `cvData` (passed as props
from `src/pages/cv.astro`) and renders a consistent wrapper:
`<section class="reveal cv-section" aria-labelledby="X-heading">` with
`<h2 id="X-heading" class="cv-eyebrow">` (`src/components/*.astro`).

Lead-ins are short descriptive labels. The decision is where they are authored and
how they reach each component without fragmenting the copy across ~14 files.

## Decision

Author all lead-ins in a single `sectionLeadIns` map in `src/data/cv.ts`, keyed by
section slug, and pass the relevant string into each section component as a
`leadIn` prop. Each component renders the prop as a subordinate line directly under
its `<h2>` (a new shared `.cv-lead` class for consistent styling).

- Single source of truth in the existing content file — matches the owner story
  and keeps page wiring in `cv.astro`.
- Testable: a unit test can assert the map covers every rendered section slug.
- The same edit pass adds a stable `id` (the section slug) to each component's
  `<section>` wrapper, giving the ADR-002 nav its anchor targets.

Lead-ins are optional per section: a slug absent from the map renders no lead-in,
so sections where a lead-in would merely restate the heading can omit it.

## Alternatives Considered

### Alternative 1: Static copy hardcoded in each component

- **Description**: Write each lead-in string literally in its component markup.
- **Pros**: No prop plumbing; copy co-located with the section.
- **Cons**: Spreads authored copy across ~14 files, contradicting the
  single-source owner story; harder to review/tune holistically; not testable as a
  set.
- **Why rejected**: Violates the "maintain in one place" requirement.

### Alternative 2: Richer per-section objects in cvData

- **Description**: Model each section as a structured object carrying its lead-in
  alongside other metadata.
- **Pros**: Most extensible.
- **Cons**: Over-engineered for a one-line label; a larger data-model change that
  risks bleeding into `cv-work-impact`'s ownership.
- **Why rejected**: YAGNI; a flat slug→string map is sufficient.

## Consequences

### Positive

- One file to edit and review all lead-ins; consistent `.cv-lead` styling.
- Section `id`s added in the same pass serve the in-page nav anchors.
- Optional entries avoid noise where a lead-in adds nothing.

### Negative

- Each of the ~14 body components gains a small, uniform edit (accept `leadIn`,
  render it, add a section `id`).

### Risks

- **Map drifts out of sync with rendered sections.** *Mitigation*: a unit test
  asserts every section slug used on `/cv` has a (possibly intentionally empty)
  entry, or that unknown keys are absent.
- **Lead-ins restate headings (noise).** *Mitigation*: keep them short and
  distinct; omit where redundant (optional entries enable this).

## Implementation Notes

- Add `sectionLeadIns: Record<string, string>` to `src/data/cv.ts` and a
  `.cv-lead` rule to `src/styles/global.css`.
- Section slugs: `summary`, `credentials`, `impact`, `expertise`, `experience`,
  `work`, `approach`, `education`, `certifications`, `publications`, `voluntary`,
  `personal`, `interests`, `links` (align with existing `*-heading` ids).
