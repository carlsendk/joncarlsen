# ADR-001: Centralise styling into a named component-class system in one cohesive pass

## Status

Accepted

## Date

2026-06-10

## Context

The CV site already centralises colour and font *tokens* (semantic CSS custom
properties mapped to Tailwind utilities) and has zero inline `style=` attributes
and zero raw colour literals in markup. However, 8-12 recurring UI patterns
(section shell, section eyebrow, entry title, body prose, meta line, links,
pills, cards, badges, impact metric) are expressed as **repeated Tailwind utility
strings duplicated ~60-80 times across 23 `.astro` files**. There is no
`@layer components` layer, so the same "role" is re-typed per component. This is
the direct cause of the recurring type-size/spacing drift the owner has reported
(e.g. body prose appearing at two sizes; meta lines using `tracking-wider` in some
places and `tracking-[0.2em]` in others; the impact heading missing `font-medium`).
The owner wants one source of truth for styles, the existing drift fixed, the
whole site covered, and a guard so drift cannot silently return.

## Decision

Define a **named component-class vocabulary** in the central stylesheet — one
class per recurring UI role — and convert every component and page across the
**whole site** (the `/cv` components, the `/impact` and `/work` index pages, and
the case-study detail layout including its long-form prose) to use those classes
instead of duplicated utility strings. During conversion, **collapse each role to
a single canonical value**, resolving the existing drift (one meta-line tracking,
one body size, consistent heading weights). Record the resulting scale as a short
written **style spec** (the canonical type scale and token-usage rules) that new
work follows, and add an **automated build/CI guard** that fails on regressions
(reintroduced raw repeated utility strings, off-scale font sizes, or colour
literals in markup). Deliver this as **one coordinated pass**, not piecemeal.

## Alternatives Considered

### Alternative 1: Incremental, role-by-role centralisation

- **Description**: Centralise one pattern family at a time (typography, then
  layout shells, then links/cards), shipping each independently, adding the spec
  and guard at the end.
- **Pros**: Lower risk per step; each change is small and easy to verify.
- **Cons**: Prolonged mixed state where some components use central classes and
  others still inline; the "single source of truth" benefit only lands at the end;
  more total review cycles.
- **Why rejected**: The owner explicitly chose whole-site coverage and a single
  cohesive pass; the site's existing design ethos (ADR-001 of cv-visual-design)
  is "one disciplined pass across all sections," and a half-converted state would
  itself read as inconsistency.

### Alternative 2: Token-first with lighter class extraction

- **Description**: Expand the design-token layer (add explicit type-scale tokens),
  write the spec and add the guard, but only extract classes for the highest-
  frequency patterns, leaving low-frequency ones (badges, single-use card) inline.
- **Pros**: Less code churn; avoids creating classes for genuinely one-off styles
  (the governance caution that a style storing its own values can become a new
  drift source).
- **Cons**: Some repeated utility strings intentionally remain; the rule "every
  recurring role has a class" is not uniformly true, leaving ambiguity about where
  the boundary sits.
- **Why rejected**: The owner wants the whole site covered and drift eliminated;
  partial extraction leaves the exact ambiguity that caused the original problem.

### Alternative 3: Cleanup only (no spec, no guard)

- **Description**: Consolidate the duplicated strings now; add no written spec or
  tooling.
- **Pros**: Lowest effort.
- **Cons**: The same drift reappears the next time components are hand-edited.
- **Why rejected**: The owner explicitly asked for the strongest drift prevention
  (an automated check).

## Consequences

### Positive

- One place to change any shared style; "consistency by default" for new work.
- The recurring drift (sizes, tracking, weights) is resolved to one canonical set.
- A written spec plus an automated guard make regressions visible and blockable.
- Markup becomes shorter and more readable (role names instead of long strings).

### Negative

- One larger coordinated change to author and verify, touching ~23 files at once.
- A new build/CI guard to maintain.
- Small, intentional visual diffs where drift is corrected (accepted by the owner).

### Risks

- **Visual regression** during mass conversion — mitigated by verifying computed
  styles before/after (the existing Playwright measurement approach) and treating
  any unintended diff as a defect.
- **Over-centralisation** turning one-off styles into brittle shared classes —
  mitigated by only creating a class for a role that genuinely recurs.
- **Tailwind v4 `@apply`/`@utility` mechanics** differ from v3 — a TechSpec
  concern, flagged for the implementation phase.
- **Performance budget** (Lighthouse >= 90) must hold — the change is CSS-structural
  and should be net-neutral or smaller; re-verify.

## Implementation Notes

Implementation specifics (exact class names, whether `@apply` / `@utility` / plain
CSS rules, and the form of the automated guard) belong in the TechSpec. This ADR
fixes only the product-level direction: a complete named-class system, whole-site
conversion, drift fixed to one canonical scale, plus a written spec and an
automated guard, delivered in one pass.
