# ADR-001: Restructure /cv by front-loading proof, adding in-page navigation, and disclosing only the long tail

## Status

Accepted

## Date

2026-06-11

## Context

The `/cv` page is the site's intentional **full overview** (the home page is the
short tier). It renders 15 sections in this order: Hero → Summary → Credentials →
Timeline → Impact → Approach → CaseStudies → Expertise → Education →
Certifications → Publications → VoluntaryLeadership → PersonalDetails → Interests
→ Links.

Two structural problems work against the reader:

1. **High-value content sits below the heaviest block.** The Impact lead-figures
   band (position 5) and Expertise / core competencies (position 8) both land
   *after* the dense 40+-bullet Timeline. Eye-tracking research on executive CVs
   shows ~80% of attention falls in the top third and a keep/reject scan happens
   in ~6–7 seconds, so proof buried below the fold is largely unseen.
2. **A 15-section page has no wayfinding.** There is no in-page navigation, and
   sections lack lead-in lines, so the page reads as an undifferentiated wall and
   forces linear scrolling.

The constraint that shapes every option: this page must remain the **full
overview**. Any approach that hides substantial content to look tidier fights the
page's purpose (and harms print and SEO).

A parallel feature, `cv-work-impact`, owns the impact/achievements/projects data
model and the auto-aggregated `/impact` page. This decision must stay disjoint
from that: it governs **order, density, and navigation of the `/cv` page only**,
not what data the bullets carry.

## Decision

Restructure `/cv` along four disciplined pillars:

1. **Reorder to front-load proof.** Move the quantified highlights/Impact band and
   Expertise (core competencies) up directly under the Summary, *above* the dense
   Timeline. Settle the remaining sections into the executive-CV order: identity →
   summary → highlights → competencies → experience → work/case studies →
   education/certifications → publications/volunteer → personal/interests → links.
2. **Add a one-line lead-in under each section heading** so readers can decide
   what to dive into without reading the whole block.
3. **Add a sticky in-page table of contents / anchor navigation** with
   current-section highlighting, so a long page becomes jump-to-section navigable.
4. **Apply progressive disclosure only to the long tail** — e.g. earlier roles and
   long certification/publication lists expand *in place*. Everything stays on the
   page (rendered, indexed, printable); headline value and recent roles are never
   collapsed.

This is the fullest of the three approaches considered, deliberately constrained
so that collapsing is the exception, not the strategy.

## Alternatives Considered

### Alternative 1: Reorder + per-section lead-ins only (lightest)

- **Description**: Keep all 15 sections, resequence to front-load proof, add a
  one-line lead-in under each heading. No in-page navigation, no disclosure.
- **Pros**: Lowest risk and effort; fixes the first-screen problem; no new
  interactive components.
- **Cons**: Leaves a long 15-section page with no wayfinding; readers still scroll
  linearly through everything; fatigue on the heavy tail is unaddressed.
- **Why rejected**: On a page this long, navigation *is* the reader experience;
  omitting it leaves the largest readability problem unsolved.

### Alternative 2: Reorder + aggressive consolidation/collapsing (heaviest hiding)

- **Description**: Resequence and aggressively merge/collapse sections behind
  accordions and "read more" to shrink the visible page.
- **Pros**: Page looks compact and tidy; less apparent scrolling.
- **Cons**: Hides real content behind clicks, directly contradicting the page's
  job as the full overview; weakens print output and reduces SEO prominence of
  collapsed text; risks fragmenting continuous narrative.
- **Why rejected**: The full-overview mandate makes hiding substantial content a
  non-starter; completeness is a hard requirement, not a nice-to-have.

## Consequences

### Positive

- Quantified proof and core competencies land in the top third where attention
  concentrates, matching how executives' CVs are actually scanned.
- The sticky in-page nav turns an exhausting scroll into a jump-to-section
  experience, the single biggest navigability gain for a long page.
- Per-section lead-ins make the whole page skimmable without sacrificing depth.
- The page stays a true full overview: nothing of value is hidden; print and SEO
  are preserved because disclosed content still renders in the document.

### Negative

- More work than a pure reorder: a new sticky-nav component and an
  expand-in-place pattern for the tail.
- Reordering touches the page composition and the relative prominence of several
  sections, requiring care to avoid regressions in spacing/rhythm.

### Risks

- **Scope creep into the impact data model.** *Mitigation*: this decision is
  explicitly limited to order/density/navigation; the bullet/impact model is owned
  by `cv-work-impact`.
- **Disclosure drifting toward hiding core content.** *Mitigation*: collapse is
  restricted to the long tail (earlier roles, long lists); recent roles and all
  top-of-page value remain always visible; expanded-in-place keeps everything in
  the rendered document.
- **Sticky nav competing with the existing sticky header.** *Mitigation*: treat
  the in-page nav as coordinated with the sticky-header work
  (`cv-sticky-header`); resolve stacking/offset during design.

## Implementation Notes

Implementation (component changes, sticky-nav mechanism, disclosure markup) is
deferred to the TechSpec. This ADR fixes only the product approach. The build
must keep the site near-zero-JS and print-friendly; the sticky nav and
expand-in-place tail should degrade gracefully and remain keyboard-accessible.
