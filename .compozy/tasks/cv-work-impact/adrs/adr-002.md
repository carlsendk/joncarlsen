# ADR-002: The Impact page is auto-aggregated from work, not separately curated

## Status

Accepted

## Date

2026-06-10

## Context

The site currently holds impact highlights in `cvData.impact`, a hand-authored
list of `metric` + `summary` entries that is independent of the project case
studies and their `metrics`. This lets the impact list drift out of sync with
the work and forces the owner to author the same number twice.

During brainstorming the owner chose an auto-aggregated Impact page and
confirmed that every notable impact of a project should surface — not just one
headline per project. Combined with ADR-001 (the bullet is the connective unit),
this makes the work/bullet the single source of every impact number.

## Decision

Derive the **`/impact` page automatically** from the metric-bearing bullets and
project metrics across all work — no separately curated impact list. Every
metric a project carries surfaces as its own achievement line on `/impact`, each
linking back to its source project. The standalone `cvData.impact` list is
retired as the source of truth; impact is owned by the work.

Ordering and grouping on `/impact` are derived (e.g. by company, theme, or the
existing `order` field), not hand-ranked per entry.

## Alternatives Considered

### Alternative 1: Keep a separately curated impact list

- **Description**: Retain `cvData.impact` as a hand-picked, hand-ordered list,
  optionally linking each entry to a project.
- **Pros**: Full editorial control over what shows and in what order.
- **Cons**: Duplicate authoring; impact and work drift out of sync; the owner
  explicitly chose auto-aggregation.
- **Why rejected**: Violates the single-source-of-truth goal from ADR-001.

### Alternative 2: One headline impact per project

- **Description**: Surface only each project's top metric on `/impact`.
- **Pros**: Tighter, more scannable aggregate page.
- **Cons**: Hides secondary achievements from the cross-cut view.
- **Why rejected**: The owner chose to surface all impacts per project.

## Consequences

### Positive

- Adding a metric to a project automatically surfaces it as an achievement; no
  second authoring step.
- Impact and work cannot drift apart — there is one source.

### Negative

- Less editorial control over the exact set and order on `/impact`; the page is
  only as curated as the underlying metrics.
- A project with many metrics contributes many lines, which could crowd the page
  if metrics are not kept to the strongest few.

### Risks

- Vanity or weak metrics would dilute the page. Mitigation: discipline at
  authoring time — keep 1–3 strong, business-outcome metrics per project (a
  content guideline, not a product flag).
- Long aggregate list as the project count grows toward ~20. Mitigation: derived
  grouping by company/theme and sensible default ordering.

## Implementation Notes

- Migrate existing `cvData.impact` entries onto their source projects as
  metrics/bullets, then remove the standalone list.
- `/impact` reads from the work/bullet metrics at build time.
