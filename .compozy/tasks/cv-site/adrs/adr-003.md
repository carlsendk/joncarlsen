# ADR-003: Astro as the static-site stack with a single content-data file

## Status

Accepted

## Date

2026-06-09

## Context

The PRD calls for a single, mobile-first, fast-loading scrolling page that the
owner can keep current with low effort (PRD: Goals, UX, Risks — staleness). The
repository is a blank slate with no existing stack. The build technology must
favor minimal shipped JavaScript (for load speed), a component structure (for
maintainable per-section markup), and a clean separation of content from
presentation (so the owner edits one data file rather than hunting through
markup).

## Decision

Build the site with Astro. Author one component per PRD section
(`Hero`, `Timeline`, `Impact`, `Links`) composed in a single `pages/index.astro`.
Keep all CV content (name, title, value proposition, roles, impact highlights,
links) in a single typed data file, `src/data/cv.ts`, that the components render.
Astro ships near-zero client JavaScript by default, producing static HTML.

## Alternatives Considered

### Alternative 1: Plain HTML + CSS

- **Description**: A hand-written `index.html` and stylesheet, no build step.
- **Pros**: Zero dependencies; absolute simplest pipeline; fastest possible load.
- **Cons**: Content is interleaved with markup, so routine edits mean editing
  HTML; no component reuse or type safety on the content shape.
- **Why rejected**: The PRD prioritizes low-effort, low-error updates; a typed
  content-data file separated from markup serves that better at negligible cost.

### Alternative 2: Next.js / React (static export)

- **Description**: A React framework with static export.
- **Pros**: Familiar React ecosystem; large component library availability.
- **Cons**: Heavier tooling and more shipped JavaScript than a static one-pager
  needs; runtime overhead works against the speed goal.
- **Why rejected**: Disproportionate to a single static page with no interactive
  logic; conflicts with the minimal-JS/fast-load goal.

## Consequences

### Positive

- Near-zero shipped JS supports the sub-1s load and mobile-first goals.
- Per-section components keep markup readable and match PRD sections one-to-one.
- A single typed `cv.ts` makes content updates fast and low-risk.

### Negative

- Introduces a build step and a small toolchain (Node, Astro) versus plain HTML.
- The owner edits TypeScript data rather than visible HTML (mitigated by the
  data file being simple, well-typed, and documented).

### Risks

- Risk: toolchain/version drift over time. Mitigation: pin dependency versions
  and keep the dependency surface minimal.

## Implementation Notes

- Structure: `src/data/cv.ts`, `src/components/{Hero,Timeline,Impact,Links}.astro`,
  `src/pages/index.astro`, `public/resume.pdf`.
- Styling via Tailwind (see ADR-005); deployment via GitHub Pages (see ADR-004).
- Note: this project has no Go; the canonical TechSpec template's Go-interface
  expectation is satisfied with the equivalent TypeScript content interface.
