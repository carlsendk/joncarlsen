# ADR-003: Hybrid content model — projects in the `work` collection, tags on the `cv.ts` spine

## Status

Accepted (refines ADR-002)

## Date

2026-06-10

## Context

The structured source (ADR-001) must hold roles, projects, achievements, skills,
and interests, tagged so subsets can be selected. The codebase already splits
content two ways (cv-content ADR-003): a typed `src/data/cv.ts` for the CV spine
(roles, impact, expertise, education, certifications, publications, personal
details, links) and a markdown `work` content collection for project case
studies, rendered at `/work/<slug>`. We must decide where the new structure and
tags live without a disruptive rewrite.

## Decision

Keep the existing split and extend both stores:

- **Projects live in the `work` collection.** Every project, featured or not, is a
  markdown entry. The schema gains `company` (string), `featured` (boolean,
  default false), `themes` (string array), and `skills` (string array) alongside
  the existing fields. Every published (non-draft) entry renders its own
  `/work/<slug>` page. The `featured` flag controls surfacing only: the frontpage
  and `/cv` show the top featured projects; the new `/projects` index lists every
  project grouped by company.
- **The `cv.ts` spine carries tags.** `Role` and `Highlight` gain optional
  `themes` (and `Role` an optional `skills`). A new `Interest` type and an
  `interests` field are added; interests render in a new section on `/cv` only.
  These tag fields are authored for every current item so the source is complete;
  they are metadata for selection (offline tailoring and the Phase 2 variants),
  not necessarily rendered in the MVP UI.

This refines ADR-002: that ADR proposed deep pages for featured projects only.
The owner chose to render a page for every project, so non-featured projects are
addressable too. The two-tier idea still holds for *surfacing* (featured on the
frontpage and `/cv`, all on `/projects`), and thin stubs are prevented by
requiring a real summary and body before a project is published.

## Alternatives Considered

### Alternative 1: Move everything into content collections

- **Description**: Move roles, impact, and interests out of `cv.ts` into markdown
  or data collections so all content is one uniform tagged store.
- **Pros**: Single mental model; uniform tagging.
- **Cons**: A large refactor of the working CV spine and its components for no new
  capability; higher regression risk on a shipped site.
- **Why rejected**: Cost without benefit; violates YAGNI.

### Alternative 2: Keep everything in `cv.ts`

- **Description**: Add projects, tags, and interests as typed arrays in `cv.ts`;
  no markdown for projects.
- **Pros**: One file.
- **Cons**: Loses per-project markdown bodies and the existing `/work` deep-dive
  rendering; long prose in a TypeScript file is awkward to author and review.
- **Why rejected**: Throws away the working case-study collection.

## Consequences

### Positive

- Minimal change to a shipped site; reuses the `work` collection, its route, and
  every section component.
- Projects scale by dropping in markdown files; the CV spine stays typed and
  type-checked.
- Tags live next to the content they describe, in both stores.

### Negative

- Two stores to keep coherent (already true today).
- Tag fields exist in two schemas (Zod for `work`, TypeScript for `cv.ts`); a
  shared vocabulary is a convention, not enforced (see ADR-004).

### Risks

- Every-project-gets-a-page can surface thin pages. Mitigation: a project is
  published only with at least a one-line summary and a real body; drafts stay
  unpublished.

## Implementation Notes

`company` is required on the `work` schema; the existing `axon-ai-platform.md`
gains `company`, `featured: true`, and tags. The `/projects` route and the
Interests section follow the established section-wrapper and heading pattern.
