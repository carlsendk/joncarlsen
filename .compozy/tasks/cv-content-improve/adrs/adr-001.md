# ADR-001: A structured, tagged content source as the single source of truth for leadership CVs

## Status

Accepted (amends cv-content ADR-002)

## Date

2026-06-10

## Context

The shipped `cv-content` feature put the CV content in a typed data file plus a
markdown case-study collection, presented as one public site with a single
leadership identity (cv-content ADR-002). The owner now wants the content to
behave "like a database I can make target CVs with": one maintained source from
which he can produce role-targeted versions of his CV and reuse the same content
for tailored job applications. He has confirmed the focus is leadership
positions throughout. He also wants richer project write-ups, room to grow to
roughly twenty projects, growable achievements, and a spare-time / interests
section.

Two constraints shape this. The site is static and near-zero-JS, so a literal
"database app" that generates a CV at runtime is out. And the identity is
leadership: targeted versions are leadership CVs that emphasise different themes
for different roles, not different career identities.

## Decision

Treat the CV content as a single structured, tagged content source (the
"database" in plain terms, not an application). Every meaningful unit (role,
project, achievement, skill, interest) carries metadata so subsets can be
selected for a given leadership role: theme/domain (for example AI and LLM,
platform and developer experience, organisational scaling and culture, cloud and
real-time data, security and compliance, transformation), company, period, and
skills. From this one source:

- The **public site** is rendered as today (frontpage, full CV, projects), with
  the default `/cv` as the canonical leadership CV.
- **Targeted leadership versions** are produced two ways, both without a runtime
  app:
  - On-site: a small set of **pre-built static variant pages** (built at deploy
    time by selecting on theme tags), each a leadership CV that leads with a
    different emphasis. No runtime filtering, no query UI, no JavaScript builder.
  - Offline: the owner (or an assistant) **selects the relevant subset** from the
    structured source to assemble a tailored leadership CV per job, in the
    existing `docs/` job-folder workflow.

This amends cv-content ADR-002 on one point only: role tailoring is no longer
strictly offline, and more than one leadership presentation may exist. It
preserves ADR-002's core: every presentation is a leadership CV, and the default
`/cv` stays the single canonical identity (the one link pasted into
applications). Targeted variants are deliberately shared alternates.

## Alternatives Considered

### Alternative 1: Interactive CV builder (runtime tag filtering)

- **Description**: A page where tags are picked and the CV is generated
  client-side.
- **Pros**: Most flexible; any combination on demand.
- **Cons**: Requires real client JavaScript and state, breaking the near-zero-JS
  and performance constraints; more to maintain; little value for a recruiter
  audience.
- **Why rejected**: Violates the static stance for a capability the audience does
  not need. Pre-built leadership variants cover the realistic angles.

### Alternative 2: Multi-track tagging (leadership, consulting, product, program)

- **Description**: Tag and target across several career identities.
- **Pros**: Broadest reach.
- **Cons**: The owner's focus is leadership; multiple identities dilute the
  message and reintroduce the problem cv-content ADR-002 already settled.
- **Why rejected**: Out of focus. Targeting is by theme within leadership, not by
  career track.

### Alternative 3: Keep tailoring fully offline (status quo)

- **Description**: Leave the site single-presentation; tailor only in documents.
- **Pros**: Simplest; no new public surface.
- **Cons**: Does not give the on-site targeted leadership versions the owner
  asked for, and leaves the content as prose rather than a reusable structured
  source.
- **Why rejected**: The owner wants both on-site variants and a structured,
  reusable source.

## Consequences

### Positive

- One maintained source feeds the public site, pre-built leadership variants, and
  offline per-job tailoring. Improvements compound everywhere.
- Theme tagging makes "which projects and achievements fit this leadership role"
  a selection, not a rewrite.
- Stays fully static and near-zero-JS; identity stays consistently leadership.

### Negative

- The content model carries more metadata to author and keep consistent.
- More than one leadership presentation exists, which must be kept coherent.

### Risks

- Near-identical variant pages could create duplicate-content/SEO and maintenance
  cost. Mitigation: keep variants few and deliberate; the default `/cv` is
  canonical; treat variants as Phase 2 and validate their value first.
- Scope creep toward a builder app. Mitigation: Non-Goals forbid runtime
  filtering, query UI, and auto-export.

## Implementation Notes

Tag vocabulary, metadata fields, and variant routing are deferred to the
TechSpec. Offline tailoring and adding the roughly fifteen further projects are
enabled by this structure, not built as part of it.
