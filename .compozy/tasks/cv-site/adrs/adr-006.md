# ADR-006: Serve the site at custom domain joncarlsen.dk on GitHub Pages

## Status

Superseded by [ADR-007](adr-007.md) — hosting moved to Netlify (2026-06-09).

Accepted

## Date

2026-06-09

## Context

ADR-004 chose GitHub Pages for hosting and flagged that the site's URL — still
an open PRD question — determines Astro's `site`/`base` configuration. The owner
has now decided the site stays on GitHub Pages but is served at the custom domain
**https://joncarlsen.dk**. A custom domain resolves the base-path fork: the site
is served from the domain root, not a `/joncarlsen` project-page subpath.

## Decision

Configure GitHub Pages to serve the existing `carlsendk/joncarlsen` repository at
the custom domain `joncarlsen.dk`. Set Astro `site: 'https://joncarlsen.dk'` and
`base: '/'`. Commit a `public/CNAME` file containing `joncarlsen.dk` so each Pages
deploy preserves the custom-domain binding. Configure DNS at the domain registrar
to point at GitHub Pages, and enable "Enforce HTTPS" in repository Pages settings.

## Alternatives Considered

### Alternative 1: Project page at carlsendk.github.io/joncarlsen

- **Description**: Serve from the default Pages URL with no custom domain.
- **Pros**: Zero DNS setup; free; immediate.
- **Cons**: URL carries a `/joncarlsen` path segment; requires `base: '/joncarlsen'`,
  complicating every asset and the PDF link; less credible on a CV.
- **Why rejected**: A clean, professional root URL matters for a job-hunting site;
  the owner owns joncarlsen.dk.

### Alternative 2: Rename repo to carlsendk.github.io (user page)

- **Description**: Rename the repo so Pages serves it at the user-page root.
- **Pros**: Clean root URL (`carlsendk.github.io`); `base: '/'`; no domain cost.
- **Cons**: Requires renaming the repo; still not a personal-brand domain.
- **Why rejected**: The owner prefers the joncarlsen.dk brand domain over a
  github.io URL.

## Consequences

### Positive

- Clean, professional root URL on a personal-brand domain.
- `base: '/'` keeps asset and PDF paths simple.
- Stays on GitHub Pages — no new host or account.

### Negative

- Requires DNS configuration at the registrar and a `public/CNAME` file.
- Initial DNS propagation and HTTPS certificate issuance add a one-time delay.

### Risks

- Risk: missing/incorrect `CNAME` file causes Pages to drop the custom domain on
  the next deploy. Mitigation: commit `public/CNAME` so it ships with every build.
- Risk: misconfigured DNS or HTTPS not enforced. Mitigation: set the documented
  GitHub Pages DNS records (apex `A`/`AAAA` records, plus a `www` `CNAME` if used)
  and enable "Enforce HTTPS"; verify the live URL after first deploy.

## Implementation Notes

- `astro.config`: `site: 'https://joncarlsen.dk'`, `base: '/'`.
- `public/CNAME`: single line `joncarlsen.dk`.
- DNS: point the apex domain at GitHub Pages' published IP addresses (and add a
  `www` subdomain `CNAME` to `carlsendk.github.io` if a `www` host is wanted).
- Enable GitHub Pages with source = GitHub Actions and turn on "Enforce HTTPS".
