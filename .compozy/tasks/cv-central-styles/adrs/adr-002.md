# ADR-002: Express style roles as @apply component classes in global.css @layer components

## Status

Accepted

## Date

2026-06-10

## Context

ADR-001 commits to a named component-class vocabulary as the single source of
truth for styling. The stack is Tailwind v4.3 wired via `@tailwindcss/postcss`,
with a single entry stylesheet (`src/styles/global.css`) that does
`@import "tailwindcss"`. Semantic colour/font tokens already exist there, mapped
into utilities via `@theme inline`. No `@apply`, `@utility`, or `@layer components`
rule exists yet; every recurring role is a duplicated utility string in `.astro`
markup. We must choose how to physically express the roles so the conversion is
(a) pixel-identical to today apart from agreed drift fixes, and (b) genuinely a
single definition per role.

## Decision

Define each recurring role as a class inside `@layer components` in `global.css`,
implemented with `@apply` over the **exact utility strings already in use**
(e.g. `.cv-section { @apply reveal mx-auto max-w-2xl border-t border-border px-6
py-14; }`). Components replace their duplicated utility strings with the role
class. Per-instance colour (`text-fg` vs `text-muted`) and one-off modifiers stay
in markup alongside the role class; only the shared, recurring portion moves into
the class. Because the classes `@apply` the same utilities, the compiled CSS is
identical to the current output, making the conversion verifiably non-visual
except where a role's value is deliberately collapsed to its canonical form.

The initial role vocabulary: `cv-section`, `cv-eyebrow`, `cv-entry-title`,
`cv-body`, `cv-meta`, `cv-link`, `cv-pill`, `cv-pill-solid`, `cv-card`,
`cv-badge`, `cv-metric`, and `cv-detail`. A role is created only where the pattern
genuinely recurs; true one-offs stay inline.

## Alternatives Considered

### Alternative 1: Plain CSS rules reading tokens directly (no @apply)

- **Description**: Spell out each role's declarations in raw CSS using the tokens.
- **Pros**: Decouples roles from Tailwind utility names; fully explicit.
- **Cons**: Re-specifies every spacing/size value by hand, risking subtle pixel
  drift versus the current utilities; loses Tailwind's responsive/variant ergonomics.
- **Why rejected**: Defeats the "verifiably pixel-identical" requirement and
  duplicates values the utilities already encode.

### Alternative 2: Astro wrapper components (<Section>, <Eyebrow>, ...)

- **Description**: Centralise roles in the markup layer as Astro components.
- **Pros**: Strong encapsulation; props-driven.
- **Cons**: Large structural rewrite (new component files, every section changed);
  doesn't match the "central CSS" intent; mixes layout and styling concerns.
- **Why rejected**: Higher churn and risk for no styling benefit over a CSS class.

## Consequences

### Positive

- Compiled CSS is identical to today (same utilities), so regression risk is low
  and verifiable.
- One definition per role; site-wide change from one edit.
- Markup shrinks to readable role names.

### Negative

- Tailwind v4 `@apply` requires the theme to be in scope; fine in `global.css`
  (the file that imports Tailwind) but a constraint to remember.
- A class that `@apply`s many utilities can hide complexity; mitigated by keeping
  roles small and named by purpose.

### Risks

- **v4 @apply mechanics**: in v4, `@apply` works in the main stylesheet without
  `@reference`; component-scoped `<style>` blocks would need `@reference`. Keep all
  role classes in `global.css` to avoid this entirely.
- **Over-centralisation**: only create a role for genuinely recurring patterns.

## Implementation Notes

- All roles live in one `@layer components` block in `global.css`.
- Keep colour utilities (`text-fg`/`text-muted`) in markup so a single role serves
  both foreground and muted contexts.
- Verify pixel-identity by comparing computed styles (font-family, size, weight,
  line-height, spacing) before/after across pages using the existing Playwright
  measurement approach.
