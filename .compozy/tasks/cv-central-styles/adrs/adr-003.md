# ADR-003: Drift guard via ESLint + Tailwind plugin plus a custom canonical-scale rule, in the build gate

## Status

Accepted

## Date

2026-06-10

## Context

ADR-001 requires an automated guard so styling drift fails the build rather than
being noticed later. The drift signals identified in the inventory live in `.astro`
markup: font sizes outside the canonical scale, colour literals (none today, but
must stay that way), and reintroduced ad-hoc utility strings for roles that now
have a class. The repo currently has no lint toolchain; the hard gate is the
Netlify build command (`npm run check && npm run build && linkinator`) plus the
Lighthouse plugin. Stock Tailwind ESLint plugins enforce class validity, ordering,
shorthand, no-contradictions, and arbitrary-value restriction, but have **no**
built-in rule for "font size must come from the canonical set" or "no colour
literal in markup."

## Decision

Add **ESLint** with a Tailwind class-linting plugin and the Astro parser, and
**one small custom ESLint rule** that flags font-size utilities outside the
canonical scale and colour literals in markup. Expose it as `npm run lint` and
wire it into the Netlify build command **before** `npm run build`, so a violation
fails the deploy. Stock plugin rules cover class hygiene; the custom rule covers
the project-specific drift signals that motivated the effort.

## Alternatives Considered

### Alternative 1: Custom dependency-free Node check script

- **Description**: A bespoke Node script that greps `src/` for drift signals.
- **Pros**: Zero new framework; rules exactly tailored; minimal maintenance surface.
- **Cons**: Reinvents class parsing; no editor integration; less conventional.
- **Why rejected**: The owner chose the ESLint approach for its conventional,
  configurable rule ecosystem and editor feedback.

### Alternative 2: Stylelint on global.css only

- **Description**: Lint the stylesheet for colour literals / token usage.
- **Pros**: Lightweight for CSS.
- **Cons**: Blind to `.astro` `class="..."` strings — misses the main drift vector.
- **Why rejected**: Cannot see where the drift actually occurs.

### Alternative 3: Stock ESLint Tailwind rules only (no custom rule)

- **Description**: Rely solely on the plugin's built-in rules.
- **Pros**: No custom rule to maintain.
- **Cons**: An off-scale size typed in markup is not caught — the exact failure
  mode this work exists to prevent.
- **Why rejected**: Leaves the primary drift signal unguarded.

## Consequences

### Positive

- Conventional, configurable linting with editor integration.
- The custom rule enforces the canonical scale — the signal that matters most.
- Runs in the existing build gate, so drift blocks deploys.

### Negative

- Introduces an ESLint toolchain (deps, config, Astro parser) to a previously
  lint-free repo, adding install/build time and maintenance.
- The custom rule is bespoke code to keep working across ESLint/plugin upgrades.

### Risks

- **Build-time cost**: ESLint over the source could slow the Netlify build; keep
  the config lean and scope it to `src/`. Re-verify build duration.
- **False positives** blocking legitimate work: scope the custom rule to clear
  signals (font-size utilities, colour literals) and allow the documented arbitrary
  values that are part of the system (e.g. `tracking-[0.2em]`).
- **Plugin/parser version skew** with Astro 6 / ESLint 9 flat config — pin
  compatible versions and verify in CI.

## Implementation Notes

- Flat config (`eslint.config.mjs`), ESLint 9, `astro-eslint-parser` +
  `eslint-plugin-astro`, plus a Tailwind class plugin (e.g.
  `eslint-plugin-better-tailwindcss` or `eslint-plugin-tailwindcss`, whichever is
  v4-compatible) — final selection during implementation.
- Custom rule: allow the canonical font-size utilities only (`text-xs`, `text-sm`,
  `text-base`, `text-xl`, `text-2xl`/`3xl`, `text-5xl`/`6xl` per the scale); flag
  others and any `#hex`/`rgb(`/named-colour utility in markup.
- Build command becomes: `npm run lint && npm run check && npm run build && linkinator`.
