# ADR-001: A persistent identity sticky header on every page with a contextual back-link

## Status

Accepted

## Date

2026-06-10

## Context

The site is a hub-and-spoke static portfolio. The home page (`/`) carries the
full `Hero` (name "Jon Østerby Carlsen", title "Executive Engineering
Leadership", value proposition), while every secondary page (`/cv`, `/impact`,
`/work`, `/work/<slug>`) renders its own inline back-link `<nav>` and relies on
the page body for identity. There is no shared header. The theme toggle floats
separately as a `fixed top-3 right-3` button, and the existing back-links are
*contextual, not uniform*: `/cv` steps back to the overview (`/`), while
`/impact`, `/work`, and `/work/<slug>` step back to `/cv`.

The owner asked for a sticky header that travels with the reader on every page,
carrying the name, the "Executive Engineering Leadership" title, dark/light mode,
LinkedIn and GitHub links, and a back-navigation affordance. During brainstorming
the owner confirmed the header should appear on **every page including home** and
stay **always visible**. The open product question was the navigation model —
specifically whether the header's back-link should flatten the current contextual
hierarchy.

## Decision

Introduce a single, shared **sticky header rendered on every page** (including
home). It carries, left-to-right in reading order: a **back-link**, the
**compact identity** (name + title), and a **utility cluster** (LinkedIn +
GitHub icon links and the dark/light theme toggle). The floating theme toggle is
**absorbed into this header** so the site has one chrome element instead of two.

The back-link is **contextual**, preserving today's step-back hierarchy:

- On `/cv` → `← Overview` to `/`.
- On `/impact`, `/work`, `/work/<slug>` → `← Back to CV` to `/cv`.
- On `/` (home) → no back-link (there is nowhere "back" to go).

The header replaces the per-page inline back-link `<nav>` blocks, which become
redundant. Identity (name + title) appears in the header on every page; on home
it coexists with the larger `Hero`, differentiated by scale rather than removed.

## Alternatives Considered

### Alternative 1: Uniform "← Overview" back-link to home on every secondary page

- **Description**: Every secondary page's header back-link reads `← OVERVIEW`
  and links to `/`, matching the owner's literal wording.
- **Pros**: One consistent label and target; simplest mental model; least
  conditional logic.
- **Cons**: Flattens the existing information architecture — a reader on a
  `/work/<slug>` case study would jump straight to home, skipping `/cv`, losing
  the natural "back to the CV I came from" step.
- **Why rejected**: Silently regresses current navigation. The owner's
  "← OVERVIEW" intent is honored as the `/cv` case of the contextual link.

### Alternative 2: Name-as-home-link, keep in-body back-links

- **Description**: The header carries no back-link; clicking the name returns
  home, and the existing contextual `← Back to CV` links stay in each page body.
- **Pros**: Least disruption to current pages; no removal of in-body nav.
- **Cons**: The header's navigation role is weaker than asked; two places own
  back-navigation (header name vs. body link), splitting the affordance.
- **Why rejected**: The owner explicitly wanted the back affordance in the
  header.

### Alternative 3: Identity only on secondary pages, utility-only header on home

- **Description**: Show name + title in the header only on secondary pages; on
  home let the `Hero` own identity and render a utility-only bar.
- **Pros**: Avoids name appearing twice on home.
- **Cons**: Contradicts the owner's confirmed choice of a persistent identity
  bar on every page including home.
- **Why rejected**: The owner chose persistent identity on home; the home
  duplication is resolved by scale (compact bar vs. large Hero), not by dropping
  identity.

## Consequences

### Positive

- One consistent chrome element travels with the reader everywhere; identity,
  profile links, and theme control are always reachable.
- Navigation hierarchy is preserved — no accidental IA regression.
- Per-page back-link `<nav>` blocks and the floating toggle are consolidated,
  reducing duplicated markup across pages.

### Negative

- Name + title appear twice on home (header bar + Hero); must be visually
  reconciled by scale so it reads as deliberate, not redundant.
- The header gains a small amount of per-page conditional logic (which back-link,
  or none on home).
- LinkedIn and GitHub icons are net-new assets — no icon files exist today.

### Risks

- A sticky bar can obscure keyboard focus and break skip-links (a known a11y
  pitfall). Mitigation: keep the bar short; ensure focusable content is not
  hidden beneath it; preserve a visible focus indicator.
- Absorbing the floating toggle changes where the `#theme-toggle` lives.
  Mitigation: the print stylesheet hides chrome by selector, so the new header
  must also be print-hidden (see ADR-002 / PRD constraints).

## Implementation Notes

- The header is a single shared component placed in the base layout so every
  route inherits it; the back-link target/label is derived per route.
- Removing the in-body back-link `<nav>` blocks is part of adopting the header.
- LinkedIn/GitHub icon SVGs and their accessible labels are new deliverables.
