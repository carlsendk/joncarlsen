# ADR-004: Impact derivation from the work collection

## Status

Accepted

## Date

2026-06-10

## Context

ADR-003 makes the `work` collection the canonical source of impact (`metrics[]`).
Three surfaces consume it and each needs a deterministic, build-time rule (no
hand-curated impact list, per ADR-002):

- **`/impact`** (new) shows the full set and needs an order/grouping.
- **Home** previously rendered five curated highlights; it needs a compact,
  non-manual subset.
- **`/cv`** needs a scannable metric band that does not repeat the timeline's
  descriptive bullets.

Observed data: seven non-draft work entries; `metrics[]` present on five of them
(both Ørsted entries have none); ten metric lines total across four companies
(AXON, DFDS, Lunar, Scrive). `featured` is set on only two entries — too few to
drive a home band.

## Decision

Derive all surfaces at build time from the `work` collection via a shared module
`src/lib/impact.ts`:

```ts
import { getCollection } from "astro:content";

export interface ImpactItem {
  company: string;
  metric: string;   // one entry per string in work.metrics[]
  slug: string;     // links to /work/<slug>
  title: string;
  order: number;
}

// every metric of every non-draft work entry, in work.order order
export async function impactItems(): Promise<ImpactItem[]>;

// the first metric of each company (the lowest-order work that has metrics)
export async function leadImpactItems(): Promise<ImpactItem[]>;
```

- **`/impact` page**: `impactItems()` grouped by company, companies ordered by
  their lowest `order`, items in `metrics[]` order. Companies with no metrics do
  not appear.
- **Home + `/cv` metric band**: `leadImpactItems()` — the first metric of each
  company (~4: AXON, DFDS, Lunar, Scrive), each linking to its work. Compact and
  fair across employers without a curation flag.

The band shows figures only (metric + company), never the case-study prose, so it
never duplicates the `/cv` timeline bullets.

## Alternatives Considered

### Alternative 1 (compact band): first metric of each *featured* work

- **Description**: Use the `featured` flag to pick the band.
- **Pros**: Reuses an existing flag.
- **Cons**: Only two entries are featured → only two numbers; too sparse for home.
- **Why rejected**: Per-company gives broader, fairer coverage at the right size.

### Alternative 2 (compact band): first N metrics overall by order

- **Description**: Take the first N metric lines across all work.
- **Pros**: Simplest rule.
- **Cons**: Over-weights the most recent work (AXON/DFDS contribute three each)
  and can omit whole companies.
- **Why rejected**: One-per-company is fairer in the same space.

### Alternative 3 (/impact): group by theme

- **Description**: Group impact lines by theme tag.
- **Pros**: Sets up Wave 3 filtering.
- **Cons**: Needs theme attached to each metric; metrics carry no theme today.
- **Why rejected**: Out of scope for Wave 1; company grouping mirrors the
  existing index and needs no new data.

## Consequences

### Positive

- All surfaces are pure functions of the work content — adding a metric updates
  them on the next build with no extra authoring.
- Home stays tight; `/cv` gains a scannable band; `/impact` reads as a
  by-employer track record.

### Negative

- A company with no work metric (Ørsted today) contributes nothing to the band or
  `/impact`. Acceptable; mitigated by adding metrics to those entries if desired.

### Risks

- The shared module imports `astro:content`; it must be imported only within the
  build/component graph (Astro pages and components), not at module top level of
  non-Astro contexts. Mitigation: keep it consumed by `.astro` files only.

## Implementation Notes

- `Impact.astro` changes its prop from `Highlight[]` to `ImpactItem[]` and renders
  metric + company, linking to `/work/<slug>`.
- `index.astro` and `cv.astro` pass `leadImpactItems()`; `impact.astro` groups
  `impactItems()` by company.
