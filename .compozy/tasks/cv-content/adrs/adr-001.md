# ADR-001: Hub-and-spoke information architecture (frontpage + full CV + growable case studies)

## Status

Accepted

## Date

2026-06-09

## Context

The live site (feature `cv-site`) is a strict single page with four sections
(Hero, Timeline, Impact, Links) holding placeholder content. The owner now wants
the real CV content from `docs/Content/_base/` on the site, plus "a way to show
the full CV and add more details than I already have."

The real content is far richer than the current four sections: a full career
history (8+ roles, each with achievement bullets), areas of expertise,
education, certifications and networks, publications and honours, a leadership
narrative, and personal details. Forcing all of it onto one page would defeat
the 7-8 second recruiter scan the site is built around; hiding it behind a PDF
breaks owner-control and the no-contact-details rule (PDFs tend to embed phone
and email). The owner also wants room to grow detail over time (project
case studies) without redesigning the site each time.

## Decision

Adopt a hub-and-spoke information architecture, all statically rendered:

- **`/` - frontpage (the hub).** A short, scannable landing tuned to the 7-8s
  scan: hero, a small set of quantified highlights, areas of expertise, a
  condensed list of recent roles, and outbound links. One clear path to the
  full CV.
- **`/cv` - the full CV (primary spoke).** One long, anchored page carrying the
  complete CV content: every role with achievement bullets, expertise,
  education, certifications and networks, publications, talks/writing, and a
  compact personal-details line. Its own shareable, ATS- and SEO-friendly URL.
- **`/work/<slug>` - case studies (growable spoke).** A content collection where
  each deep-dive is a single markdown file that generates its own page and is
  auto-linked from `/cv` and the frontpage. The owner adds detail over time by
  dropping in a markdown file, with no layout changes.

Navigation between tiers is plain links (no JavaScript expand/collapse), so each
tier stays fast, accessible, and independently shareable.

## Alternatives Considered

### Alternative 1: Single long page with progressive disclosure

- **Description**: Keep one route; hide depth behind native `<details>` or
  minimal JS "show more" toggles.
- **Pros**: One URL; no routing; preserves the original single-page model.
- **Cons**: One very heavy page; weaker scan; collapsed content is less
  shareable and less SEO-visible; adds interaction state to maintain.
- **Why rejected**: Linking achieves the same disclosure with better
  performance, accessibility, and shareability, and keeps the frontpage genuinely
  short.

### Alternative 2: Frontpage + downloadable PDF as the "full CV"

- **Description**: Short HTML frontpage; the full CV is a PDF download.
- **Pros**: Familiar; recruiters can save it.
- **Cons**: Hard to keep in sync with the site; not owner-editable in one place;
  PDFs typically carry phone/email, conflicting with the no-contact-details
  rule (ADR-002 of `cv-site`); weaker for SEO and on mobile.
- **Why rejected**: Conflicts with owner-control and anti-spam constraints; a
  static `/cv` page is more maintainable and is print-friendly anyway.

### Alternative 3: Topic subpages (`/experience`, `/leadership`, `/writing`)

- **Description**: Split the CV across several themed routes instead of one
  `/cv`.
- **Pros**: Smaller individual pages.
- **Cons**: No single shareable "my CV" link; more navigation and more pages to
  keep consistent; fragments the recruiter's evaluation.
- **Why rejected**: A recruiter wants one CV link, not a site to navigate. One
  `/cv` page with anchors serves this better.

## Consequences

### Positive

- Frontpage stays genuinely short and serves the fast scan; `/cv` serves deep
  evaluation; case studies serve proof - each at its own URL.
- Growing detail is additive (drop in a markdown file), with no redesign.
- Fully static and owner-controlled; no contact surface; print-friendly `/cv`
  gives a "PDF" for free via the browser.

### Negative

- More routes and templates to build and keep visually consistent than a single
  page.
- Content now spans a typed data model plus a markdown collection, a slightly
  larger surface to maintain.

### Risks

- Frontpage/`/cv` duplication could drift. Mitigation: both read from one typed
  content source so shared facts are single-sourced.
- Case-study scope creep. Mitigation: seed only 1-2 at launch; the collection is
  optional and grows on demand.

## Implementation Notes

Routing, content-collection schema, and component structure are deferred to the
TechSpec. The existing design/token system from `cv-visual-design` is reused
across all tiers.
