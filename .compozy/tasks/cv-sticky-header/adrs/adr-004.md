# ADR-004: Retain the inline theme flash guard; bundle the click handler

## Status

Accepted

## Date

2026-06-10

## Context

The theme toggle moves from its floating corner into the new header. During
technical review the owner asked for "no inline, and follow best practices" for
the toggle's scripts. The toggle involves two distinct scripts:

1. A **pre-paint flash guard** in `<head>` that reads the persisted/OS theme and
   sets `.dark` on `<html>` before first paint.
2. A **click handler** that toggles `.dark`, persists the choice, and syncs
   `aria-pressed`.

Both are currently `is:inline`. Removing the guard's inline nature is the crux:
a bundled ES-module script is deferred and runs *after* first paint, which
reintroduces a flash of the wrong theme — violating the PRD's no-flash success
criterion. An external **render-blocking** classic script in `<head>` avoids the
flash but is itself a documented performance anti-pattern (render-blocking
requests are exactly what Lighthouse flags), and the project enforces a
Lighthouse performance budget ≥ 0.90 via `netlify.toml`. A grep confirmed the
site sets **no Content-Security-Policy** (no CSP meta tag, no `_headers`, none in
`netlify.toml`), so there is no security constraint that forbids inline scripts.

## Decision

Apply "follow best practices" as the governing instruction and do **not** apply
"no inline" to the critical theme guard:

- Keep the **flash guard inline in `<head>`** (a minimal classic script). This is
  the documented standard for theme-flash prevention (mirrored by Tailwind's
  dark-mode guidance, `next-themes`, and similar), it satisfies the no-flash
  criterion, and it protects the Lighthouse performance budget by avoiding an
  extra render-blocking request.
- Convert the **click handler to a standard Astro-processed `<script>`** (bundled,
  deferred module) inside the `ThemeToggle` component — this is the genuine
  best-practice improvement over `is:inline` for non-critical interactivity.
- Keep `ThemeToggle.astro` as its own component, composed into `Header.astro`,
  with its `fixed top-3 right-3 z-50` positioning removed so it sits in the
  header's flex row.

## Alternatives Considered

### Alternative 1: External render-blocking guard (`/theme-init.js`)

- **Description**: Move the guard to a same-origin classic `<script src>` in
  `<head>` with no `defer`/`type=module`.
- **Pros**: Literally "no inline code"; still runs before paint, so no flash.
- **Cons**: Render-blocking external request is a recognized performance
  anti-pattern and counts against the enforced Lighthouse perf budget; web.dev's
  own remedy for this class of issue is to *inline* the small critical script.
- **Why rejected**: Trades the documented best practice for the thing tooling
  flags, to satisfy a constraint (no inline) that has no backing requirement (no
  CSP) on this site.

### Alternative 2: Remove all inline including the guard (bundled/deferred only)

- **Description**: Honor "no inline" literally; initialise theme from a deferred
  module.
- **Pros**: Zero inline script anywhere.
- **Cons**: Deferred init runs after first paint → flash of the wrong theme on
  every load; violates the approved no-flash criterion.
- **Why rejected**: Directly contradicts a PRD success criterion.

### Alternative 3: Pure CSS `prefers-color-scheme`, no JS guard

- **Description**: Initial theme purely from the OS media query; manual toggle
  still JS.
- **Pros**: No JS guard at all; no flash for users matching their OS.
- **Cons**: A persisted manual override that differs from the OS flashes/reverts
  on load; weakens the persistent manual choice the toggle exists to provide.
- **Why rejected**: Degrades the core toggle behavior.

## Consequences

### Positive

- No theme flash; persistent manual override preserved; Lighthouse perf budget
  unaffected.
- The interactive handler follows Astro's recommended bundled-`<script>` pattern.

### Negative

- One small inline script remains in `<head>`, against the literal "no inline"
  ask. Documented here with rationale (best practice + no CSP + perf budget).

### Risks

- If a strict CSP is introduced later, the inline guard would need a nonce/hash
  or externalisation. Mitigation: revisit this ADR if a CSP is ever added.

## Implementation Notes

- The inline guard can stay essentially as-is (`Base.astro` lines ~26–42); only
  the toggle's interactive script changes from `is:inline` to a processed
  `<script>`.
- `ThemeToggle` loses its positioning utilities and renders inside the header.
