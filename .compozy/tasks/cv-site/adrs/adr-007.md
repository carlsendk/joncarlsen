# ADR-007: Host on Netlify (supersedes the GitHub Pages mechanism)

## Status

Accepted — supersedes ADR-004 and ADR-006.

## Date

2026-06-09

## Context

ADR-004 chose GitHub Pages and ADR-006 chose the custom domain `joncarlsen.dk`
on Pages, both reasoning that Netlify would "require a new account and external
service dependency." During task_05 go-live this premise turned out to be false:

- The owner already has a Netlify account (team "Carlsens sites").
- A Netlify site (`joncarlsen`, id `94d39d54-…`) is already **connected to the
  `carlsendk/joncarlsen` repo** and already serves `joncarlsen.dk` with the
  custom domain bound and HTTPS enforced — apex DNS points at Netlify, not Pages.
- The Pages path (ADR-006) would have required repointing apex DNS from Netlify
  to GitHub Pages IPs (registrar access + propagation + cert re-issue).

So GitHub Pages was the *more* setup, not less. The only reason the old site was
stale was an outdated build config (`gatsby build` / publish `public/`).

## Decision

Host on **Netlify**, deploying from the existing repo-connected site. A
committed `netlify.toml` is the source of truth: build command
`astro check && astro build && linkinator …` (publish `dist/`, Node 22), plus
`@netlify/plugin-lighthouse` for performance/accessibility budgets. Push to
`master` builds, gates, and deploys; the domain + HTTPS are already in place.
GitHub Pages is disabled.

## Alternatives Considered

### Alternative 1: GitHub Pages + repoint DNS (ADR-004/006)

- **Pros**: co-located with the repo; the task_05 Actions workflow already worked.
- **Cons**: requires apex DNS repoint away from Netlify, propagation delay, cert
  re-issue, and binding the domain in Pages settings — all to leave a platform
  that already serves the domain.
- **Why rejected**: strictly more setup than staying on Netlify.

## Consequences

### Positive

- Zero DNS work — domain and HTTPS already live on Netlify.
- Push-to-deploy from the existing repo connection; deploy previews + rollbacks.
- `base: '/'` serves correctly at the apex root (no project-subpath asset breakage
  that Pages had at `carlsendk.github.io/joncarlsen/`).

### Negative

- A second platform (but already owned and in use).
- The rich GitHub Actions lhci gate (proven red-green) is replaced by the Netlify
  Lighthouse plugin, whose deploy-blocking behavior was accepted on its documented
  design rather than independently red-tested live (owner decision). The
  deterministic gates — `astro check` and the link check — still hard-block the
  deploy via the build command's non-zero exit.

## Implementation Notes

- `netlify.toml` committed; GitHub Pages disabled via API; `.github/workflows/`,
  `lighthouserc.json`, and `public/CNAME` removed.
- `astro.config` `site: 'https://joncarlsen.dk'` / `base: '/'` are unchanged and
  correct for the apex root.
